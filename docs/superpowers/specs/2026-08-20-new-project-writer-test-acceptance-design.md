# New-Project FairyGUI Writer 测试与验收证据设计

日期：2026-08-20  
范围：`codex/uir-v1` 的通用新建工程 FairyGUI XML Writer  
明确不包含：Project Binding、村庄专用逻辑

## 目标

交付一套可复跑的核心测试与验收包。它证明通用 Writer 能生成确定性的 FairyGUI 6.1.4 工程，能通过一个真实 Editor 代表工程的保存闭环，并对三类关键失败输入安全拒绝。每个用例必须有一张能支持判定的截图，不能以无上下文的“全绿终端”代替产物或错误证据。

## 用例矩阵

| ID | 类型 | 目的 | 通过条件 | 截图必须展示 |
|---|---|---|---|---|
| TC-01 | 正向 | 正常生成 FairyGUI ZIP | 命令成功；ZIP 可重开；成员闭包、XML 和 PNG 校验通过 | ZIP 名称、成员列表、校验结论 |
| TC-02 | 正向 | 证明确定性 | 相同输入连续构建两次；ZIP SHA-256 和字节完全一致 | 两个 SHA-256、字节一致结论 |

## 证据架构

### 可复跑执行器

新增一个测试证据执行入口，复用生产 CLI、现有 fixtures 和验证器，不复制 Writer 逻辑。执行器为每个用例生成结构化结果：输入摘要、命令或 API 边界、预期、实际、公开错误码、产物哈希、发布状态和 PASS/FAIL。

执行器不得记录本机私有绝对路径、环境变量、资源原始字节或异常私密 cause/context。机器结果采用 canonical JSON，并记录代码提交、FairyGUI 版本和执行时间。

### 截图

自动化用例先生成一页本地只读证据卡，再使用浏览器截图。每页只展示一个用例，包含足以复核判定的产物成员、哈希或稳定错误码。截图不依赖外网，也不发送数据。

真实 Editor 用例使用 FairyGUI 6.1.4 的单一中立代表工程。截图只证明正确工程窗口已打开；Unity/FairyGUI 若仍不支持状态截图接口，则本用例不得虚构截图成功。此时用可审计的 Editor 窗口枚举证据卡作为截图，并由机器 transcript 记录双保存动作和四项哈希。该限制必须在报告中明确。

### 交付文件

- `docs/validation/2026-08-20-new-project-writer-test-acceptance.md`：人读报告。
- `docs/validation/2026-08-20-new-project-writer-test-results.json`：机器可读结果。
- `docs/validation/evidence/new-project-writer/`：六张截图，一例一张。
- 可复跑测试/脚本位于现有 `tests/` 或项目既有工具目录，并纳入 pytest。

## 运行与判定

1. 每个用例独立准备输入，避免共享可变状态。
2. 自动化用例执行实际生产入口或其公共边界，而不是只断言 mock 调用。
3. 失败用例必须同时断言稳定公开错误和输出未发布。
4. 截图生成前，从机器结果重新计算展示字段，避免报告与实际输出漂移。
5. 六例全部 PASS 才能给出总体 PASS；任一截图缺失、与机器结果不一致或无法支持判定，则该例 FAIL。
6. 最终运行全量 pytest、Ruff、mypy 和 `git diff --check`。

## 范围约束

- 村庄只是一份通用映射回归样例；禁止依据页面名、节点 ID 或需求方词汇分支。
- 本轮不设计或实现 Project Binding。
- 不把单一 Editor 代表工程扩写成 11/11 GUI 证据。
- 不声称截图证明其未实际展示的对象可见性、可访问性或视觉一致性。

## 验收标准

- 六个用例均有完整步骤、预期、实际、PASS/FAIL 和一张有效截图。
- 自动化结果可在干净工作区复跑并得到相同结构化结论；确定性用例得到相同 ZIP SHA-256。
- Editor 用例的动作、窗口标题、版本与四个文件哈希由 durable transcript 记录。
- 报告与 JSON、截图字段交叉一致，仓库内链接有效。
- 不引入 Project Binding、村庄特例或私密信息泄漏。
