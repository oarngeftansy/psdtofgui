# PSD → FGUI 质量审查（2026-09-28）

> 这是修复前审查快照。后续处理、真实材料的新计数与剩余缺口见[按严重程度修复记录](2026-09-28-severity-repairs.md)，不要沿用下文的旧门禁或 34 项结论。

范围：`codex/hifi-replacement-plugin` 工作树当前代码（含未提交的原位替换修复）、真实 RAR/主页 PSD 的既有证据。本次只审查，未修改业务逻辑。结论：仍是验证中的原型，不能作为已达标的无损替换工具交付。当前真实会话仍被 34 项待处理门禁阻断，本次没有批准候选。

## P1：验收可能漏检或错误放行

### 1. 全页验收实际裁成旧组件大小

`src/figma_to_fgui/api.py:1947` 从旧 inventory 取宽高，再用 `composite_region_path(source, 0, 0, width, height)` 裁 PSD。真实旧组件为 1080×1920，PSD 为 1080×2340，因此底部 420 像素不参与比较。`fairygui_editor_verify.py` 只要截图等于这一尺寸且有图像，就把 `full_frame` 设为 true。

后果：报告里的“完整截图/视觉等价”并不保证覆盖完整 PSD，更不保证画布外可见滚动内容。应明确完整内容范围与视口范围，分别验收，不能裁掉差异来取得通过。

### 2. 自动接受没有类型兼容硬约束

`hifi_mapping.py:108` 把类型不兼容当成加权分数的一部分；`:259` 对 matched 自动写入 accept。同名、同位置、同大小可以抵消类型错误。

独立内存复现：从真实 inventory 取一个 image，构造同名同位置的 TEXT；结果 `matched, score=0.895, action=accept, unresolved=0`。不是生产会话决策。

后果：数字下降不代表对应正确。写入端也不会对所有无资源的错误类型配对报错，有些配对只改几何而不替换视觉。应先排除不兼容类型，再检查全局一对一及视觉/语义证据。

### 3. “最多 5 个对象”计数仍不符合逐对象要求

`hifi_mapping.py:272` 遇到已占用的组直接返回，`:278` 将整个未匹配分支加入一行，`:322` 按行统计未解决数。根 inventory 也只枚举直接 displayList，未展开所有实例视觉叶子。

独立内存复现：20 个可见叶子组成一个未匹配组，结果只有 1 行、1 项 unresolved。

真实 PSD 有 108 个有效可见层，其中 81 个非 group 层；适配后只有 75 个节点，2 个合成组使 33 个可见层不再独立出现在映射清单。合成不等于像素必然丢失，但缺少逐层覆盖证明。当前 34 行不能解释为 34 个完整盘点的独立视觉对象。

### 4. 批准门禁没有同时要求完整解析和 Editor 证据

`hifi_patch.py:681` 对解析不完整仅添加 warning，`:692` 的 approvable 只看 lossless blockers 和行为遮挡。`api.py:2016` 使用 `review.approvable OR editor_verification.approvable`，并未强制两种检查均成立。UI 同样采用 OR。

独立 fixture 复现：`parse_coverage_complete=False, editor_check_required=True, approvable=True`。因此无 PSD blockers 的输入可能只靠人工勾选完成批准，不必真正运行 Editor。另一方面，单次静态像素相同可以绕过 review 中的无损阻断，却没有验证所有状态。

应将结构、解析覆盖、逐对象映射覆盖、各受影响状态、完整视觉范围和候选哈希绑定为分别必须通过的门禁。人工勾选不是自动检测结果。

### 5. 合成组资源存在“裁整页并补背景”的非无损路径

`psd_source_store.py:250` 从 PSD 整页内嵌合成图获取像素。对于 group，`:280` 调用 `_erase_masked_pixels`，按文字包围框扩大蒙版，再用邻近像素均值补洞（`:32`）。结果不是该组独立的透明分层渲染，可能烘焙进组外背景并改变文字下面的装饰。

真实适配器识别出 2 个这类合成组。当前复杂组件写入门禁可阻止部分调用路径，但资源生成逻辑本身仍在，不能称为无损能力。本次修复的“不新增兄弟覆盖对象”没有自动消除资源内部烘焙背景的问题。

## P2：能力与产品表述不一致

### 6. 程序结构不变不等于程序行为通过

当前保护主要比较 XML 身份、类型、Controller/Gear/Transition/Relation 等结构；自动 Editor 验证只渲染一个默认状态。上轮隔离诊断只替换背景 image 和图标 loader，并在 Editor 中验证了未修改按钮的红点控制器两页。

这些证据不能证明 Delegate/Reward 视觉改写后仍正确，也没有证明实际游戏绑定、点击热区、不同数据值、动态布局或所有动画状态。`HifiReplacementReviewPanel.tsx` 的保护通过文案应明确是结构检查，不能让用户理解为行为验收已经完成。

### 7. 核心按钮的原位替换仍未实现

`hifi_patch.py:395` 对组件内部需要映射的场景阻断；`:415` 对 graph 等不能接受 raster 的场景阻断。正确阻断比覆盖层冒充更安全，但仍是未实现目标，不是完成替换。真实页面仍有 34 项待处理、五类无损证据未闭合。

### 8. “明确对应”按钮处理的实际是 suggested

`apps/web-console/src/App.tsx:258` 把 `status === suggested` 标为“接受明确对应”。映射引擎 suggested 可来自 0.55 以上的启发式；匹配主要使用精确名称、位置、面积、类型、父级和顺序，且按旧对象顺序贪心占位，尚未使用全局匹配或实际图像证据。

当前真实会话因超过 5 项而禁用此按钮，但对较小输入会出现。建议把建议与已证实对应分开，百分比分数也不能表述为校准后的正确概率。

### 9. 刷新恢复与启动数据路径不统一

`App.tsx:75` 起的工程、PSD、会话和阶段都是内存 state，没有恢复入口；刷新后回准备页。后端文件仍在，但用户不能在界面直接继续。

当前手动服务使用 `local-run/current-source/data`；`Start-Hifi-Replacer.ps1` 默认使用工作树 `.local-hifi-run/data`，并重新选择空闲端口。用户重启脚本可能看到另一个数据目录和网址，造成材料/会话丢失的错觉。当前没有已验证的桌面 exe 冷启动交付。

## 验证边界与处理顺序

上轮 Python 全量 1362 项通过、前端相关测试通过，说明已覆盖路径的回归检查通过；不等于本次真实输入全页端到端验收通过。本次三个内存/fixture 探针均复现了现有测试未覆盖的规则漏洞，没有改真实映射或批准任何会话。

优先修复完整验收范围、自动接受的硬约束、逐叶子覆盖计数、批准门禁及非无损合成资源路径；再实现嵌套原位替换和多状态验证；最后补会话恢复与可复现启动交付。安装 FGUI MCP 可改善操作入口，不能替代这些应用逻辑修复。
